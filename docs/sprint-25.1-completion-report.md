## 5. Scope implementations completed

Real, server-side query filtering, using only existing relationships (no new
data modeled):

- **`sales.order.view` — `OWN_RECORDS`**: `SalesOrder.salesAgentId` (always
  the authenticated caller who created the order).
- **`sales.order.view` — `OWN_TEAM`**: `Employee.managerEmployeeId` resolves
  the caller's direct reports; each report's linked `User.id` filters
  `salesAgentId`. Required a new, narrow, read-only `SalesModule → HrModule`
  dependency (`SalesOrderController` injects `EmployeeService` directly,
  never a repository — the same pattern `AccessControlModule` already
  established for HR). `SalesOrderService` itself still has zero HR imports,
  unchanged, proven by `direct-sales-independence.spec.ts`'s existing
  structural guards.
- **`hr.attendance.view` — `DEPARTMENT`/`OWN_TEAM`**: extended the exact
  `hr.employee.view` mechanism Sprint 25 built (same `managerEmployeeId`/
  `departmentId` columns) to `AttendanceController.list()`.

Precedence when a caller's role union grants more than one scope for the
same permission: broadest-satisfiable-scope-wins (`ORGANISATION` >
`OWN_TEAM` > `OWN_RECORDS`/`DEPARTMENT` > deny) — established and documented
this sprint since Sprint 25 never had to define it (nothing granted multiple
scopes on one permission before).

## 6. Scope limitations (honest, not oversights)

- **`ASSIGNED_TERRITORY`** and **`ASSIGNED_ASSETS`** remain unenforced — no
  server-side relationship links a `User` to a `Territory` or an `Asset`
  anywhere in the schema. A caller whose only granted scope is one of these
  gets an empty result set, never unrestricted access. Building real
  enforcement needs a new explicit assignment relationship first, which the
  brief's own instructions ("do not grant territory access merely because
  the user belongs to the Sales department") forbid inferring any other way.
- **`ASSIGNED_RECORDS`** for `maintenance.work_order.complete` — the
  underlying data (`WorkOrder.assignedToId`) already exists and supports
  real enforcement, but wiring the query-level filter was not reached this
  sprint. Flagged as the single highest-value next scope-enforcement target.

## 12. Seed changes and idempotency results

`permissionsSeeded` went from 88 → 121 across two full re-seed runs with
identical counts both times (confirmed idempotent). `RolePermission` rows
for Boby Bites went from 167 → 188. Role/User/UserRole counts unchanged
(13 active roles + 2 archived test roles created during live audit
verification; 6 users; 12 user-role assignments) — new permissions were
added only as grants to existing roles, never new roles or users.

**Why grants changed, not just counts:** several seeded custom roles (Head
of Finance, Production Manager, Maintenance Manager, Sales Manager, Sales
Team Lead, Field Sales Agent) held only a `.manage` permission for a
resource whose reads were newly split into a separate `.view` permission
this sprint. Before this sprint those `GET`s were unprotected, so every role
could browse them regardless of what they held; centrally guarding the
reads without also granting the new `.view` permission would have silently
taken away functionality these roles need (e.g. a Field Sales Agent must be
able to browse existing customers before creating a sales order — not new
capability, the same thing they could always do). Audited every newly-split
view/manage pair against each seeded role's own stated purpose and added the
missing companion grant; each addition is commented `// Sprint 25.1` in
`prisma/seed.ts` with its specific rationale. Also completed Head of
Finance's own "Full Finance access" self-description, which several
mutation actions (journal create/void, credit notes, supplier invoice
management, cash account management, cashflow management, decision
management) had never actually been reachable for under Sprint 25's design
(they were Owner/Administrator-only via the old `RolesGuard`, regardless of
role name) — now that they're real, grantable permissions, Head of Finance's
description is honored rather than left silently incomplete.

## 23. Architectural decisions and trade-offs

- **Coarse `.manage` grouping over per-CRUD-verb permissions**, following
  Sprint 25's own established precedent rather than the brief's own
  illustrative (more granular) example — chosen for consistency with the
  existing 88-entry catalogue's actual shape rather than introducing a
  second, finer-grained convention alongside it. Documented in
  authorization-coverage.md §7 as a deliberate choice, not an oversight.
- **View/manage split applied selectively**, only where a genuine
  least-privilege tension existed or the brief's own example structure
  called for it (Finance credit notes, Sales customers, Production BOMs,
  Maintenance plans, HR org structure/policies/training, Product Catalogue,
  Retail territories) — not applied uniformly everywhere, to avoid
  permission-count inflation without a real access-control reason.
- **`SalesModule → HrModule` new dependency**, accepted deliberately (§5) to
  implement genuinely-provable `OWN_TEAM` enforcement rather than leaving a
  seeded role's scope grant silently unenforceable. Scoped narrowly (the
  controller injects `EmployeeService` only, never a repository), matching
  the exact precedent `AccessControlModule` already set for the identical
  reason.
- **Broadest-satisfiable-scope-wins precedence**, established this sprint
  since it was previously undefined (no permission had multiple scopes
  granted across roles before). Chosen because Sprint 25's own "multiple
  roles combine additively" principle implies the union should reflect the
  most permissive of what was actually granted, not the most restrictive.
- **Did not attempt `ASSIGNED_TERRITORY`/`ASSIGNED_ASSETS` enforcement**,
  even though genuinely valuable, because doing so honestly would require
  inventing a new assignment relationship the brief's own instructions
  explicitly forbid guessing at ("do not grant territory access merely
  because the user belongs to the Sales department").
- **Did not attempt frontend permission-aware navigation**, per the brief's
  own "do not redesign the entire frontend navigation system unless
  necessary" — treated as out of scope for a backend hardening sprint,
  documented as the concrete next step instead of silently deferred.
