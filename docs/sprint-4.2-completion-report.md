# Sprint 4.2 Completion Report — Supplier Management

**Date:** 2026-08-02
**Status:** Complete

## 1. Objective

Implement Supplier Management — the master data source for every vendor an organisation
buys goods or services from. Explicit constraints from the brief: build only Supplier
Management (no Purchase Orders, Goods Receiving, Invoices, or Procurement workflows),
match the production quality of every module already built (Identity, Workspace,
Organisation, Users, Product Catalogue), and produce a reusable Supplier domain that
Procurement can build on top of in Sprint 4.3.

## 2. Implementation Summary

### A second non-Identity domain, built the same way Product Catalogue was

`apps/api/src/suppliers/supplier/` mirrors the Sprint 4.1 Product Catalogue module's shape
exactly: `SupplierRepository` (thin Prisma access, tenant-scoped by `organisationId`),
`SupplierService` (business rules: code generation), `SupplierController` (HTTP surface +
audit calls), and `SupplierModule` (imports `IdentityModule` for `AuditService`/
`RoleService` and `AuthModule` for `JwtAuthGuard`/`RolesGuard` — no `FileStorageModule`,
since Supplier has no image/file field, unlike Product).

### Schema — one new model, two new enums

Migration `20260802163405_add_supplier_management` adds `Supplier`
(`organisationId`-scoped, `onDelete: Cascade`) plus `SupplierCategory`/`SupplierStatus`
enums. Key decisions:

- **`supplierCode`** (`SUP-000001`, ...) — globally unique, immutable, generated by the
  same collision-avoidance loop as `ProductService.generateUniqueCode` (Sprint 4.1),
  checked via `SupplierRepository.existsByCode` with no `organisationId` filter.
- **`status`** — only two states (`ACTIVE`/`INACTIVE`, defaulting to `ACTIVE`), no
  directional lifecycle unlike Product's Draft→Active→Archived. Per the brief, this is a
  plain field on `POST`/`PATCH` rather than dedicated activate/archive endpoints — the
  Create/Edit dialog lists "Status" directly among its fields.
- **Contact/location fields** (`contactPerson`, `email`, `phoneNumber`, `website`,
  `country`, `state`, `city`, `address`, `taxIdentificationNumber`) — all optional free
  text except `email`/`website`, which are format-validated when present.
- No `DELETE` endpoint exists at all (brief: "Do not implement delete. Suppliers should
  instead become INACTIVE").

### Audit logging with a status-aware `PATCH`

Because status changes go through the same `PATCH` endpoint as every other field (not a
separate activate/archive action), `SupplierController.resolveUpdateAuditAction` inspects
the request body the same way `UserController.resolveUpdateAuditAction` already does: a
`status: "ACTIVE"` request records `supplier.activated`, `status: "INACTIVE"` records
`supplier.deactivated`, and anything else records the generic `supplier.updated` — if a
request changes both status and other fields, the status event wins.

### API and authorization — identical shape to every prior domain

`GET`/`POST /api/suppliers`, `GET`/`PATCH /api/suppliers/:id`. `GET` requires only
authentication; every write requires `@Roles('Owner', 'Administrator')` via the existing
`RolesGuard`. Tenant isolation follows `ProductController`'s convention: every lookup
resolves `(id, organisationId)` together, so a cross-tenant id 404s exactly like a
nonexistent one.

### Validation

`packages/validation/src/suppliers.ts` — `createSupplierSchema`, `updateSupplierSchema`,
and the two enum schemas as plain string literals, matching `catalogue.ts`'s convention.
`supplierCode` is absent from both schemas (server-generated only); `status` is present in
both (unlike Product, where it's excluded and only reachable via dedicated endpoints).

### Frontend — `/settings/suppliers`, reusing the Sprint 3.5 shell

- **Table** — Supplier Code, Supplier Name, Category, Contact Person, Phone, Status,
  Actions, matching the brief's exact column list.
- **Search + filters** — client-side substring search (name/code/contact person) plus
  status and category `<select>` filters, all combinable, no pagination (small-dataset
  convention established by Product Catalogue).
- **Empty state** — shown only when the organisation has zero suppliers.
- **`SupplierDialog`** — one reusable component for both Create and Edit, with every field
  from the brief (name, display name, contact person, email, phone, website, country,
  state, city, address, tax ID, category, notes, status). Unlike `ProductDialog`, there is
  no image control and no create/edit-mode field difference — every field is available in
  both modes since there's no upload-needs-an-id constraint here.
- **Workspace integration** — "Suppliers" in the sidebar and the `/workspace` dashboard's
  Platform Modules grid now point at `/settings/suppliers` and lost their "Coming Soon"
  state (added in Sprint 3.5.1); every other future module (Asset Register, Maintenance,
  Procurement, etc.) is untouched and still shows "Coming Soon."

### Seed data

`prisma/seed.ts` gained a `seedSuppliers` function: 5 hardcoded Boby Bites suppliers
(Fresh Farms Ltd, Golden Oil Ltd, PackRight Nigeria, Salt Masters Ltd, Lagos Cartons Ltd —
codes `SUP-000001`–`SUP-000005`, realistic Nigerian contact/location details, all
`ACTIVE`), upserted by `supplierCode` the same way products are upserted by `code`.

## 4. Known Limitations

- No Purchase Orders, Goods Receiving, Invoices, Vendor Payments, Procurement Workflows,
  Contracts, Price Lists, or Product–Supplier relationships — all explicitly out of scope
  per the brief, reserved for Procurement (Sprint 4.3+).
- Category is a fixed Prisma enum, not a tenant-configurable taxonomy — matches the
  brief's explicit "Use an enum" instruction.
- "Inactive suppliers cannot receive future Purchase Orders" is a stated business rule
  with nothing to enforce it against yet, since Purchase Orders don't exist in this
  codebase.
- Frontend search/filters are client-side over the already-fetched list, not a live server
  round-trip — a deliberate simplicity choice matching the Product Catalogue's "small
  dataset, fetch in full, no pagination" convention; the backend's `?search=`/`?status=`/
  `?category=` params exist and are covered by controller tests, but the frontend doesn't
  call them per-keystroke.

## 5. Deferred / Future Work

Per `docs/backlog.md` Epic 4, Procurement (Sprint 4.3+) is expected to build directly on
this foundation: Purchase Orders will reference `Supplier.id` instead of a free-text
supplier name, and inactive suppliers should become ineligible for new Purchase Orders once
that workflow exists. No changes to Supplier Management itself should be needed for that
integration beyond adding the relevant foreign key on the Procurement side.
