# Sprint 4.1 Completion Report — Product Catalogue Foundation

**Date:** 2026-08-01
**Status:** Complete

## 1. Objective

Implement the Product Catalogue — the master source of truth for every product an
Organisation manufactures or sells, and the first core Manufacturing module built on top
of the Identity foundation (Sprints 0 through 3.5). Explicit constraints from the brief:
build only the Product Catalogue (no Inventory, Production, Pricing, Procurement, or
Sales logic), stay MVP-focused, and establish patterns reusable across every future
business module. This is also the first business domain module outside `identity/` —
every architectural principle from Sprint 0 onward (modular monolith, shared-database
multi-tenancy, role-name authorization, audit-everything, `FileStorage` port abstraction)
had to carry over unchanged, not be reinvented.

## 2. Implementation Summary

### A new domain, built the same way Identity was

`apps/api/src/catalogue/product/` is the first NestJS domain module outside `identity/`,
and deliberately mirrors that module's shape exactly: `ProductRepository` (thin Prisma
access, every method tenant-scoped by `organisationId`), `ProductService` (business rules:
code/slug generation, status-transition validation, image upload orchestration),
`ProductController` (HTTP surface + audit calls), and `ProductModule` (imports
`IdentityModule` for `AuditService`/`RoleService`, `AuthModule` for `JwtAuthGuard`/
`RolesGuard`, and `FileStorageModule` directly for `FILE_STORAGE` — the same three-import
shape `UserModule`/`SettingsModule` already use). No new architectural pattern was
introduced; this sprint is a proof that the Identity-domain conventions generalize to a
real second domain, per the brief's "establish patterns reusable across future business
modules."

### Schema — one new model, three new enums

Migration `20260801184041_add_product_catalogue` adds `Product` (`organisationId`-scoped,
`onDelete: Cascade`) plus `ProductCategory`/`ProductType`/`ProductStatus` enums. Every
field decision reused an existing convention rather than inventing a new one:

- **`code`** (`PRD-000001`, ...) — globally unique, immutable, generated by
  `ProductService.generateUniqueCode`, a collision-avoidance loop identical in shape to
  `OrganisationService.generateUniqueOrganisationCode` (Sprint 3.2), except the sequence
  is global rather than name-derived, matching the brief's literal `PRD-000001`,
  `PRD-000002`, `PRD-000003` example.
- **`slug`** — derived from `name` at creation, deduped per organisation
  (`@@unique([organisationId, slug])`), same `slugify` + suffix-on-collision approach as
  `OrganisationService.generateUniqueSlug`. Not yet used in any route (the API is
  `:id`-based) — reserved for a future customer-facing catalogue page.
- **`imageUrl`/`imageKey`** — the exact `FileStorage` port + absolute-URL + opaque-key
  pattern `Organisation.logoUrl`/`logoKey` (Sprint 3.4) and `User.avatarUrl`/`avatarKey`
  (Sprint 3.5) already established. `ProductService.setImage`/`removeImage` follow the
  identical upload → store → best-effort-delete-previous-file sequence as
  `UserService.setAvatar`/`removeAvatar`.
- **`createdById`/`updatedById`** — plain nullable string columns with no FK relation to
  `User`, matching `AuditLog.actorUserId`'s existing convention (metadata about who
  acted, not a relationship the aggregate depends on) — avoided touching the `User` model
  at all.
- **`unit`** — free-text column (brief: "Store as text"), not an enum — same convention
  as `Organisation.currency`/`dateFormat` (Sprint 1B.1/3.4: free-text columns, a
  constrained dropdown in the UI only). `packages/validation/src/catalogue.ts` exports
  `PRODUCT_UNIT_SUGGESTIONS` (Piece, Pack, Carton, Bottle, Sachet, Kilogram, Gram, Litre)
  purely to drive that dropdown.

### Status lifecycle and transition validation

`DRAFT` (default) → `ACTIVE` → `ARCHIVED`, with `ARCHIVED` → `ACTIVE` also valid (an
"un-archive" path) — products are never physically deleted, per the brief.
`ProductService.activate`/`archive` reject an already-`ACTIVE`→activate or
already-`ARCHIVED`→archive call with a `400 BadRequestException` rather than silently
succeeding, satisfying the brief's "Enforce ... Valid status transitions."

### API and authorization — identical shape to every prior domain

`GET`/`POST /api/products`, `GET`/`PATCH /api/products/:id`,
`POST /api/products/:id/activate`, `POST /api/products/:id/archive`,
`POST`/`DELETE /api/products/:id/image`. `GET` requires only authentication; every write
requires `@Roles('Owner', 'Administrator')` via the existing `RolesGuard` — exactly the
brief's "Owner: Full access, Administrator: Full access, Member: Read only, No permission
engine." Tenant isolation follows `UserController`'s convention: every lookup resolves
`(id, organisationId)` together, so a cross-tenant id 404s exactly like a nonexistent one
rather than leaking existence.

### Validation

`packages/validation/src/catalogue.ts` — a new file (not appended to `identity.ts`, since
Catalogue is a distinct domain per ADR-002) with `createProductSchema`,
`updateProductSchema`, and the three enum schemas as plain string literals (no
`@prisma/client` import, matching `identity.ts`'s existing rationale: this package is
shared by `apps/web`). `code` and `status` are deliberately absent from both schemas —
`code` because it's always server-generated, `status` because it only changes through the
dedicated activate/archive endpoints, keeping status-transition validation centralized in
one place (`ProductService`) rather than allowing an arbitrary status via `PATCH`.

### Frontend — `/settings/products`, reusing the Sprint 3.5 shell

Built under the existing `(app)` route group (`apps/web/src/app/(app)/settings/
products/`), so it inherits `WorkspaceLayout` (Sidebar/Topbar) automatically with zero
navigation duplication:

- **Table** — Image, Code, Name, Category, Type, Status (colour-coded badge: Draft =
  warning/amber, Active = success, Archived = default/muted), Updated, Actions, matching
  the brief's exact column list.
- **Search** — simple client-side filter by name/code substring (brief: "No pagination");
  the backend's `GET /api/products?search=` param also exists and is exercised by a
  controller test, though the frontend currently filters the already-fetched list rather
  than round-tripping per keystroke.
- **Empty state** — a dedicated "No products yet" card with a "Create Your First Product"
  call to action, shown only when the catalogue is genuinely empty (not when a search
  filters everything out, which gets its own "No products match ..." row).
- **`ProductDialog`** — one reusable component for both Create and Edit (brief: "Edit
  Product: Reuse the same dialog"), following the exact `CreateUserDialog`/
  `EditUserDialog` pattern from Sprint 2.2. The Product Image control
  (`ImageUploadCard`, reused verbatim from Sprint 3.4/3.5) only renders in Edit mode: the
  brief lists "Product Image" as a Create-dialog field, but `POST /api/products/:id/image`
  needs an id that doesn't exist until the create `POST` round-trips, so Create mode shows
  an explanatory note instead ("You can add a product image after creating this
  product") and Edit mode shows the real upload control — the same two-step reality
  every "upload during creation" flow in this codebase has always had (Organisation logo
  and User avatar both work the same way: the entity must exist first).
- **`ProductViewDialog`** — a read-only details modal (brief: "drawer or modal ... no
  separate page required"), built on the existing shared `Dialog` primitive rather than a
  new slide-in drawer component, since the brief explicitly allows either.
- **Workspace integration** — `navigation-config.ts`'s Products entry now points at
  `/settings/products` with `comingSoon` removed; the `/workspace` dashboard's Quick
  Actions card and Platform Modules grid tile were updated to match (and the Platform
  Status card's "Product Catalogue: Coming Next" line now reads "✓ Complete," with
  "Procurement" taking its place as the next module).

### Seed data

`prisma/seed.ts` gained a `seedProducts` function: 5 hardcoded Boby Bites products
(Plantain Chips, Potato Chips, Roasted Groundnut, Kulikuli, Chin Chin — all
`SNACKS`/`FINISHED_PRODUCT`/`ACTIVE`, codes `PRD-000001`–`PRD-000005`, no images per the
brief), upserted by `code` the same way the organisation/roles/users are upserted by their
own natural keys. Codes and slugs are hardcoded (not generated via `ProductService`) since
the seed script runs outside the NestJS DI container — same reasoning `BOBY_BITES_
ORGANISATION_CODE` is hardcoded rather than generated.

## 4. Known Limitations

- No variants, batch numbers, expiry dates, barcode/QR code generation, taxes,
  multi-image galleries, or bulk import/export — all explicitly out of scope per the
  brief.
- No Inventory, Pricing, Procurement, or Sales integration — `Product.id` is the intended
  integration point for those future domains, but nothing consumes it yet.
- Category and Product Type are fixed Prisma enums, not a tenant-configurable taxonomy —
  matches the brief's explicit "hardcoded values" instruction for Category.
- The Create Product dialog cannot attach an image in the same request as creation (the
  upload endpoint needs an existing product id) — documented in the dialog itself
  ("You can add a product image after creating this product") rather than silently
  omitted.
- Frontend search is client-side over the already-fetched list, not a live server
  round-trip per keystroke, even though the backend's `?search=` param supports that —
  a deliberate simplicity choice for a catalogue with "no pagination" (i.e. expected to
  stay small enough to fetch in full).

## 5. Deferred / Future Work

Per `docs/roadmap.md` Phase 2, Procurement is the next Core Manufacturing & Commerce
domain. When Inventory/Production/Sales are eventually built, they should reference
`Product.id` directly rather than duplicating product data, per this domain's "master
source of truth" framing — no changes to the Product Catalogue itself should be needed
for that integration beyond adding the relevant foreign keys on the _other_ domains'
models.
