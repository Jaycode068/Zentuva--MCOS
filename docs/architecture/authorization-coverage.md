## 2. Classification definitions

- **`CENTRAL_PERMISSION_GUARDED`** — `PermissionsGuard` + `@RequirePermission(key)`. The authoritative, intended end-state for every private, non-self-scoped endpoint.
- **`AUTHENTICATED_ONLY`** — `JwtAuthGuard` only, no permission/role check. Every remaining instance (18, listed in §4) has been individually reviewed and is either inherently self-scoped (operates only on the caller's own record via their JWT `sub`, so no permission model is needed) or a deliberate, documented open-by-design capability. None is an oversight.
- **`NO_AUTH_GUARD`** — genuinely public (health check, registration, login, refresh, password reset, invitation accept). Reviewed individually in §5.
- **`LEGACY_RBAC_GUARDED`** — the old `@Roles(...)`/`RolesGuard` mechanism. **Zero remaining** as of this sprint.

## 6. Keeping this current

This document is generated, not hand-maintained — see
`docs/architecture/authorization-coverage.md`'s companion extraction script
described here (not committed as a repo tool this sprint; the technique, so a
future sprint can rebuild it in five minutes): walk every `*.controller.ts`
file, find its class-level `@Controller(...)`/`@UseGuards(...)`, split the
class body into per-method blocks at each 2-space-indented closing brace, and
for each block containing an HTTP method decorator (`@Get`/`@Post`/`@Patch`/
`@Put`/`@Delete`) read off `@UseGuards`/`@Roles`/`@RequirePermission`/
`@RequireCommonAccess`. Cross-checked against a live `nest start` boot log
(every route Nest actually maps) to confirm nothing was missed. Re-run after
any controller change — a route added without a matching row here is the
signal this document has gone stale.

## 7. Permission mapping rules applied this sprint

Per the brief's explicit priority order:

1. **Search the existing 88-entry catalogue first.** The large majority of
   this sprint's 469 migrations reused an existing permission key exactly —
   e.g. `sales.order.create`, `procurement.purchase_order.view`,
   `maintenance.work_order.assign` all existed in Sprint 25's catalogue but
   had never been wired to their route (see §9's "orphaned permission"
   finding).
2. **Add a new permission only for a genuine gap** — an action that existed
   in the app but had no catalogue entry at all. 33 new permissions were
   added this sprint (121 total, up from 88 — still a coherent, curated set,
   not "hundreds"). Every new key follows the established
   `module.resource.action` convention and the established coarse-grouping
   precedent Sprint 25 itself set (e.g. `finance.budget.manage` already
   covered create/edit/approve/activate/close/revise/lines as one
   permission) — new keys group closely-related mutations the same way
   rather than inventing a finer-grained convention alongside the existing
   one inconsistently. Full list in
   `apps/api/src/identity/authorization/permission-catalogue.ts`, each
   annotated `// Sprint 25.1 additions`.
3. **View/manage split, consistently.** Wherever a resource has both reads
   and writes gated, the established Sprint 25 pattern (e.g.
   `finance.invoice.view` / `.create` / `.issue` / `.cancel`) was followed:
   a separate `.view` permission for `GET`, `.manage` (or a specific verb)
   for mutations. **`.manage` never implies `.view`** — this system has no
   permission hierarchy; a role needing both must be granted both
   explicitly (access-control.md §4 "module-level vs resource/action-level
   access"). This exact rule surfaced and fixed a real bug during live
   verification — see §9.

## 8. Bugs found and fixed during this sprint (via live verification, not guessed)

Live-testing each classification change against real seeded users surfaced
four genuine, pre-existing or newly-introduced defects — listed here in full
because the brief explicitly asks not to hide gaps:

1. **Orphaned catalogue permissions** — Sprint 25 had already added
   `maintenance.work_order.create`, `maintenance.work_order.assign`,
   `sales.order.create`, `sales.order.cancel`, `sales.fulfilment.create`,
   and `distribution.dispatch.create` to the catalogue and even granted them
   to seed roles, but never actually wired `@RequirePermission` onto the
   corresponding routes — those six endpoints were still silently on
   `RolesGuard`/`@Roles('Owner','Administrator')`. Found by re-running the
   classification script after the bulk codemod pass (it still showed
   `LEGACY_RBAC_GUARDED` for these six) and fixed by hand.
2. **`GET /finance/trial-balance` and `GET /finance/accounts/:id/activity`
   mis-mapped to `finance.journal.view`** instead of
   `finance.trial_balance.view` during the bulk codemod pass. Finance
   Staff's own seeded role description ("Trial Balance, account activity,
   and selected financial reports") explicitly promises this access, and
   Finance Staff was granted `finance.trial_balance.view` but not
   `finance.journal.view` — so live-testing "Finance Staff can access
   Trial Balance" (the brief's own scenario 2) failed with a 403 until this
   was corrected.
3. **`finance.cash_account.manage` bundled read and write into one
   permission**, which meant Cash Officer — deliberately restricted from
   creating/editing/deactivating cash accounts — could not even see the
   cash account they were supposed to transact against, since granting
   `.manage` for read access would have over-privileged the role. Fixed by
   splitting into `finance.cash_account.view` (granted to both Cash
   Officer and Head of Finance) and `finance.cash_account.manage` (Head of
   Finance only).
4. **`AccessRoleController`'s "role not found in this organisation" case
   threw `BadRequestException` (400)** instead of `NotFoundException`
   (404) — inconsistent with every other domain's tenant-isolation
   convention in this codebase ("a cross-tenant id 404s exactly like a
   nonexistent one"). Found via live tenant-isolation testing (scenario 16)
   and fixed; does not leak cross-tenant existence either way (the message
   was already generic), so this was a convention bug, not a data leak.

Also surfaced and fixed (not a bug, a **regression risk**): several seeded
custom roles (Head of Finance, Production Manager, Maintenance Manager,
Sales Manager, Sales Team Lead, Field Sales Agent) held only a `.manage`
permission for a resource whose `GET` routes were newly gated behind a
separate, sibling `.view` permission this sprint. Before this sprint those
`GET`s were unprotected (`AUTHENTICATED_ONLY`), so every role could browse
them regardless; centrally guarding the reads would have silently taken away
functionality these demo roles genuinely need (e.g. a Field Sales Agent must
be able to browse existing customers before creating a sales order — that's
not new capability, it's the same thing they could always do). Fixed by
auditing every newly-split `view`/`manage` pair against each seeded role's
own stated purpose and adding the missing companion `.view` grant — see
`prisma/seed.ts`'s `// Sprint 25.1` comments for the specific additions and
their rationale. Re-seeding twice confirmed idempotency held throughout.

## 9. Scope model — semantics preserved, enforcement extended

`NONE`/`ORGANISATION`/`OWN_RECORDS`/`OWN_TEAM`/`DEPARTMENT`/
`ASSIGNED_RECORDS`/`ASSIGNED_TERRITORY`/`ASSIGNED_ASSETS` retain exactly the
meaning Sprint 25 established (access-control.md §5) — unchanged this
sprint. In particular: `NONE` as an explicit `RolePermission.scope` value
means "granted, but scoped to nothing" (never unrestricted); an _absent_
scope on a `SCOPABLE` permission is denial, not a fallback to
`ORGANISATION`; and a scope this sprint has not mechanically implemented is
never silently treated as satisfied — the caller gets an empty result set,
not unrestricted access, exactly like an unproven scope always has.

### Newly mechanically enforced this sprint

| Permission           | Scope         | How it's proven                                                                                                                                                                                                                               | Precedence when multiple scopes are granted                                                                           |
| -------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `sales.order.view`   | `OWN_RECORDS` | `SalesOrder.salesAgentId` ("always the authenticated caller", per its own schema comment) — no new data.                                                                                                                                      | `ORGANISATION` > `OWN_TEAM` > `OWN_RECORDS` > deny                                                                    |
| `sales.order.view`   | `OWN_TEAM`    | `Employee.managerEmployeeId` (existing relationship) resolves the caller's direct reports; each report's linked `User.id` filters `salesAgentId`. Unlinked reports are excluded, never crash. Zero direct reports → empty page, not an error. | (see above)                                                                                                           |
| `hr.attendance.view` | `DEPARTMENT`  | `Employee.departmentId` via the caller's own linked Employee — the exact `hr.employee.view` pattern Sprint 25 already established, extended to attendance.                                                                                    | `ORGANISATION` > `DEPARTMENT` / `OWN_TEAM` (mutually exclusive by role design; not both proven from one relationship) |
| `hr.attendance.view` | `OWN_TEAM`    | `Employee.managerEmployeeId`, same as `hr.employee.view`.                                                                                                                                                                                     | (see above)                                                                                                           |

`hr.employee.view`'s `OWN_TEAM`/`DEPARTMENT` enforcement is unchanged from
Sprint 25 (documented here for completeness, not re-implemented).

### Still recorded, not mechanically enforced (honest limitation, not an oversight)

- **`ASSIGNED_TERRITORY`** (`sales.order.view`, `sales.customer.view`,
  `sales.order.create`, `sales.customer.manage`) — no server-side
  relationship links a `User` to a `Territory` anywhere in the schema (only
  `Customer.territoryId`/`Outlet.territoryId` exist, and neither has a
  reciprocal "which users are assigned here" field). A role granted only
  this scope gets an empty result set on `GET` endpoints — never
  unrestricted access — and the grant is still fully visible in the Roles
  UI and the Effective Access Preview so an administrator can see it's
  recorded. Building real territory-assignment enforcement needs a new
  explicit assignment relationship (e.g. a `TerritoryAssignment` join
  table), deliberately out of scope for a hardening sprint per the brief's
  own "do not grant territory access merely because the user belongs to
  the Sales department" instruction — inferring it any other way would be
  exactly the kind of guess the brief forbids.
- **`ASSIGNED_ASSETS`** — no asset-to-user assignment/custodian relationship
  exists in the schema beyond `Asset`'s own custodian field, which is a
  free-text/employee reference, not a queryable "assets assigned to this
  user" index. Same honest-denial behavior as `ASSIGNED_TERRITORY`.
- **`ASSIGNED_RECORDS`** (`maintenance.work_order.complete`'s scope,
  `sales.order.view` for Field Sales Agent) — `WorkOrder.assignedToId`
  exists and _could_ support this, but wiring real query-level filtering
  for it was not reached this sprint; recorded, previewable, not yet
  mechanically filtered. Flagged here explicitly as the highest-value
  target for the next scope-enforcement pass, since the data already
  supports it.

## 13. Frontend integration — reviewed, one real gap found, not fixed this sprint

Reviewed sidebar navigation, the Access Control admin pages, and one
representative denied-access flow live in a browser (§13 scenario 18).

**Finding:** the frontend does **not** filter sidebar/module navigation by
the caller's effective permissions — `WORKSPACE_NAV_GROUPS`
(`apps/web/src/components/workspace/navigation-config.ts`) is static and
shows every module to every authenticated user regardless of what they can
actually do inside it. A user with zero Finance grants still sees the full
Finance module in their sidebar, including every sub-page tab, and only
discovers they lack access when a page's data fetch 403s and surfaces a raw
`"Missing required permission: <key>"` message.

**Not fixed this sprint**, deliberately: the brief's own guidance is "do not
redesign the entire frontend navigation system unless necessary," and this
is a UI-completeness gap, not a security one — the backend is and remains
authoritative (confirmed by scenario 17: hiding a button never was, and
still isn't, what prevents an action). Fixing it properly needs the
frontend to fetch the caller's effective access on load and filter
`WORKSPACE_NAV_GROUPS` by "has any permission in this module" — a real,
scoped, boundable follow-up task, not a rewrite. Recorded here as the
concrete next step rather than left implicit.

**Also true and unchanged:** the Access Control admin pages
(`/settings/access/*`) already refresh effective access after a role
assignment/removal (React Query cache invalidation on mutation, Sprint 25),
so no stale-permission-state bug exists there specifically.

## 14. Future work before Workflow and Notifications

Unchanged from Sprint 25's own list, still accurate:

- `EffectiveAccessResolver`/`PermissionsGuard` are the reusable
  authorization primitive a Workflow approval-routing engine or a
  Notification recipient resolver should consume directly, not re-derive.
- The audit event shape (organisation/actor/target/role/permission/
  before/after/timestamp) is already the shape a Notification engine would
  consume to decide who to notify about an access change.
- Genuinely new for this sprint: `ASSIGNED_RECORDS` scope enforcement for
  `maintenance.work_order.complete` (data already supports it —
  `WorkOrder.assignedToId` — just not wired) is the highest-value next
  scope-enforcement target, since a real assignment relationship already
  exists and nothing new needs to be modeled first.
- Frontend permission-aware navigation filtering (§14) should land before
  Workflow ships, so a workflow approval step's UI doesn't have the same
  "shown but non-functional" problem this sprint found in Finance.
